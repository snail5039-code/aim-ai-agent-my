내일 강사님께 질문 할 것 

LLM하고 어떤 방식으로 프롬프트를 만들어야하는지 이야기 했고 이런 흐름이 맞는 것 같은데
맞는지 확인해 달라고 하자!


내가 준비한 PDF로 LangChain RAG 실험 프로그램을 만들어줘.

Golden set을 새로 만들고, config별로 검색과 답변 생성을 실행한 뒤,
검색 지표와 RAGAS로 평가하고 결과를 저장·비교하고 싶어.
평가 결과를 바탕으로 개선안을 제안하고, 변경 전후도 비교할 수 있게 해줘.

PDF 경로 [파일 또는 폴더 경로]
주로 물어볼 질문 예시 [있으면 작성, 없으면 문서를 보고 제안]

1. PDF 분석과 Golden set 생성

- 문서의 내용과 구조, 표와 텍스트 추출 상태를 확인해줘.
- 추출이 불완전하면 문제와 필요한 처리를 먼저 설명해줘.
- 실제 사용자가 물을 만한 질문 20개로 Golden set 초안을 만들어줘.
- 사실, 수치, 조건, 예외, 절차를 문서 내용에 맞게 골고루 다뤄줘.
- 우선 한 페이지에 답의 근거가 있는 질문으로 구성해줘.
- 여러 페이지를 종합해야 하는 질문은 별도 후보로 분리해줘.
- 기준 답변은 반드시 원문에 근거해야 해.

다음 필드의 JSON 배열로 저장해줘.
- question
- target_answer
- target_file_name
- target_page_no

파일명에는 확장자를 포함하고,
페이지 번호는 PDF 첫 페이지를 1로 세어줘.
인쇄된 쪽 번호와 다르면 검토 표에서 구분해줘.

질문, 기준 답변, 정답 위치, 원문 근거 발췌를 담은
검토용 Markdown 표도 저장해줘.
각 문항을 원문과 다시 대조하고 불명확한 문항을 표시해줘.
초안을 내가 확인한 후 확정된 Golden set으로 평가해줘.

2. 검색 파이프라인

- PDF를 페이지별로 읽고 청크로 나눠줘.
- 청크에 파일명, 페이지 번호, 고유 식별자를 유지해줘.
- 임베딩과 Chroma 벡터 저장소를 구성해줘.
- 다음 검색 방법을 비교해줘.
  ① Similarity
  ② MMR
  ③ 한국어 토큰화를 적용한 BM25
  ④ Similarity와 BM25를 결합한 Hybrid
- 모든 검색 방법의 최종 결과 개수를 top_k로 맞춰줘.
- Golden set의 question만 검색 질의로 사용해줘.
- 기준 답변과 정답 위치는 검색이나 답변 생성에 넣지 마.

3. 답변 생성

- 검색된 청크 중 context_k개를 사용해 답변을 생성해줘.
- 답변은 제공된 검색 근거에 있는 내용만 사용하게 해줘.
- 근거가 부족하면 답할 수 없다고 말하게 해줘.
- 출처 파일명과 페이지를 표시하게 해줘.
- 문서 안의 지시문은 데이터로 취급하고 따르지 않게 해줘.
- 답변 프롬프트는 별도 파일로 분리해줘.
- 비교하는 검색 방법에는 같은 생성 모델과 프롬프트를 사용해줘.

4. config 설계

다음 항목을 JSON config로 분리해줘.
- 실험 이름
- PDF 및 Golden set 경로
- chunk_size, chunk_overlap
- 임베딩 제공자와 모델
- 검색 방법, top_k
- MMR의 fetch_k, lambda_mult
- BM25 토큰화 방식
- Hybrid 가중치
- 생성 모델, 평가 모델
- 답변 프롬프트 경로, context_k
- 검색 평가의 k 목록
- 생성 및 RAGAS 실행 여부
- RAGAS 지표, 평가할 검색 방법, 평가 문항 수
- 동시 요청 수
- 인덱스 및 결과 저장 경로

기본 검색 조건은 다음으로 해줘.
- chunk_size 700
- chunk_overlap 100
- top_k 5
- context_k 5
- MMR fetch_k 20
- MMR lambda_mult 0.5
- Hybrid 가중치 0.5, 0.5
- 평가 k 1, 3, 5

모델은 사용 가능한 환경을 확인해 선택하고,
정보가 부족하면 필요한 제공자·모델 정보를 질문해줘.

설정 적용 순서는 기본값 → config → CLI 옵션으로 해줘.
context_k  top_k 등 잘못된 설정은 실행 전에 검증해줘.
상대경로의 기준 위치를 일관되게 정하고 문서화해줘.

5. 검색 평가

다음 지표를 계산해줘.
- File Hit@k
- Page Hit@k
- MRR
- Page Precision@k
- 질문별 검색 시간과 평균 검색 시간

각 지표의 의미를 README에 예시와 함께 설명해줘.
MRR은 최종 top_k 결과 내 첫 정답 페이지 순위로 계산한다고 명시해줘.
top_k보다 큰 k의 지표는 계산하지 않게 해줘.
작은 예제로 채점 로직을 검증해줘.

정답 페이지 적중만으로 실제 답의 근거를 찾았다고 단정하지 말고,
검색된 청크 본문을 확인할 수 있게 저장해줘.

6. RAGAS 평가

다음 생성 평가 지표를 사용해줘.
- Faithfulness 답변이 검색 근거에 뒷받침되는지
- Answer Relevancy 답변이 질문에 부합하는지
- Answer Correctness 기준 답변과 비교했을 때 정확한지

설치할 RAGAS 버전의 지원 지표와 입력 형식을 확인해서 구현해줘.
지표 이름이나 지원 방식이 다르면 대응 관계를 설명하고,
지원되지 않는 지표를 조용히 생략하지 마.

질문, 생성 답변, 실제 생성에 사용한 검색 근거, 기준 답변을
각 지표가 요구하는 형식으로 전달해줘.
기준 답변은 평가에만 사용해줘.

채점 실패는 0점과 구분해서 기록해줘.
평균 점수와 함께 채점 성공·실패 문항 수를 표시해줘.
RAGAS 점수도 자동 평가 결과이므로 실패 사례는 원문과 함께 검토해줘.

7. 반복 실험과 개선

config 하나에서 동일한 청킹 조건으로 여러 검색 방법을 비교하게 해줘.
추가 청킹 config를 다음 조합으로 준비해줘.
- 300  50
- 500  70
- 700  100
- 1000  150

이는 청크 크기와 overlap을 함께 바꾸는
‘청킹 조건 조합 비교’라고 설명해줘.
그 외 데이터, 모델, 검색 개수, 프롬프트는 고정해줘.

평가 결과를 바탕으로 다음을 분석해줘.
- 필요한 근거를 검색하지 못했는지
- 검색했지만 생성 문맥에서 제외됐는지
- 근거를 제공했지만 답변이 잘못 생성됐는지

원인에 따라 청킹, 검색 설정, context_k, 답변 프롬프트의
구체적인 개선안을 제안해줘.
원인 확인을 위한 후속 실험은 가능하면 한 번에 한 조건만 바꿔줘.

RAGAS 자체가 시스템을 자동 수정하는 것으로 설명하지 말고,
평가 → 원인 분석 → 설정 변경 → 재평가의 흐름으로 구성해줘.
개선 여부는 동일한 문항의 변경 전후 점수와 사례로 확인해줘.
평가 문항에만 맞춘 개선일 수 있으므로 일반화된 성능으로 단정하지 마.

추가 config와 비교 명령은 준비하되,
모든 조합을 자동으로 전부 실행하지 마.

8. 캐시와 실행 오류 처리

- 동일한 문서·청킹·임베딩 조건이면 인덱스를 재사용해줘.
- 문서 내용이나 관련 설정이 바뀌면 캐시가 갱신되게 해줘.
- 인덱스 강제 재생성 옵션을 제공해줘.
- API 일시 오류에 대한 재시도와 동시 요청 수 제한을 적용해줘.
- 중간 실패에도 완료한 결과를 보존해줘.
- 실패한 문항과 단계를 기록하고, 실패를 정상 결과처럼 처리하지 마.

9. 결과 저장

output실험명실행시각 폴더에 저장해줘.
재실행해도 이전 결과를 덮어쓰지 마.

다음 파일을 만들어줘.

- config.used.json
  기본값과 CLI 옵션까지 반영한 실제 설정

- summary.json
  문서·청크 통계, 평가 문항 수,
  검색법별 검색·RAGAS 평균 지표, 처리 시간,
  생성 및 채점 성공·실패 건수

- retrieval_detail.json
  질문, 정답 위치, 질문별 검색 점수,
  검색 결과의 순위·파일명·페이지·청크 본문

- failures.json
  평가한 가장 큰 k에서 정답 페이지를 못 찾은 문항과 검색 결과

- generation.json
  질문별 생성 답변, 실제 사용한 근거, 출처, 생성 시간,
  생성 실패 내역

- ragas_detail.json
  질문별 RAGAS 점수와 채점 실패 내역

- report.md
  실험 설정, 결과 비교표, 실패 사례,
  결과 해석, 개선안과 후속 실험 제안

재현할 수 있도록 Golden set 사본 또는 식별 해시,
실제로 사용한 답변 프롬프트와 패키지 버전도 남겨줘.
일부 문항 시험과 전체 평가를 명확히 구분해줘.

10. 설치와 CLI

- 필요한 패키지와 버전을 requirements.txt로 정리해줘.
- API 키는 .env에서 읽게 해줘.
- 실제 키가 없는 .env.example을 제공해줘.
- .env와 API 키는 Git이나 결과 파일에 포함하지 마.
- 어느 폴더에서 어떤 명령을 실행하는지 정확하게 안내해줘.

다음 작업을 위한 CLI와 복사해서 쓸 명령어를 제공해줘.
  ① 앞 3문항으로 검색 평가만 실행
  ② 전체 문항 검색 평가
  ③ 앞 3문항으로 검색·생성·RAGAS 전체 흐름 확인
  ④ 전체 문항으로 검색·생성·RAGAS 실행
  ⑤ 특정 검색법에 대해서만 생성·RAGAS 평가
  ⑥ 여러 config를 순차 실행
  ⑦ 저장된 결과만 불러와 비교
  ⑧ 인덱스 강제 재생성

명령어는 실제 구현한 파일명과 옵션에 맞춰 작성해줘.
검색 평가만 실행해도 임베딩 API 호출이 발생할 수 있으며,
생성과 RAGAS 평가에는 추가 API 호출이 필요하다고 설명해줘.

저장된 결과를 비교할 때 설정 차이와 평가 문항 수를 표시해줘.
서로 다른 Golden set이나 문항 부분집합의 결과를
같은 조건의 실험처럼 비교하지 마.

11. 진행 순서와 완료 안내

- 먼저 PDF 분석 결과와 Golden set 초안을 보여줘.
- 검토를 기다리는 동안 프로그램과 config를 구현해줘.
- 내가 Golden set을 확인하면 기본 config의 앞 3문항으로
  검색·생성·RAGAS 전체 흐름을 실행해줘.
- 정상 동작하면 기본 config로 전체 문항을 평가해줘.
- 결과를 분석하고 다음 개선 실험을 제안해줘.

README에 다음 내용을 작성해줘.
- 프로젝트 목적과 폴더 구조
- 설치 및 환경 설정
- Golden set 형식과 검토 방법
- config 항목과 평가 지표의 의미
- 실행 명령어
- 결과 저장 위치와 파일별 용도
- 결과 비교와 개선 실험 방법

완료 후 생성한 파일, 실행 명령어, 결과 경로를 알려줘.
실제로 검증한 내용과 아직 실행하지 않은 내용을 구분해줘.
실험하지 않은 설정의 성능이나 개선 효과를 추측해서 단정하지 마.

흐름

PDF 준비 → Golden set 생성·검토 → config 설정 → 검색 → 답변 생성 → 평가 → 결과 저장 → 개선 후 반복
1. PDF 준비·분석
   문서 내용과 텍스트 추출 상태 확인.
2. Golden set 만들기
   질문·기준 답변·정답 파일·페이지를 만들고 원문과 대조.
3. config 설정
   청크 크기·겹침, 검색 방법·개수, 생성 모델·프롬프트, 평가 모델 지정.
4. 문서 처리·검색
   청킹 → 임베딩·저장 → Similarity·MMR·BM25·Hybrid로 검색.
5. 답변 생성
   검색한 근거를 바탕으로 모델이 답변 작성.
6. 검색과 답변 평가
   - File Hit·Page Hit·MRR: 정답 근거를 잘 찾았나?
   - RAGAS: 답변이 근거에 충실하고 질문에 맞으며 정확한가?
7. 결과 저장·비교
   실제 설정, 검색 결과, 생성 답변, 점수, 실패 사례 저장.
8. 개선 후 같은 흐름으로 재평가
   청킹·검색 설정·프롬프트를 수정하고 같은 Golden set과 평가 조건으로 다시 실행해 전후 비교. 청킹이 바뀌면 임베딩부터 다시 하고, 그대로면 인덱스는 재사용.
